# Event-Driven Architecture Design - Fitness Tracker

## 1. Анализ событий в системе

### 1.1 Основные события (Events)
События — это факты, которые уже произошли в системе. В нашем проекте выделены следующие доменные события:

| Событие | Описание |
| :--- | :--- |
| `UserRegistered` | Пользователь успешно зарегистрирован в системе |
| `WorkoutCreated` | Создана новая тренировка (заготовка) |
| `ExerciseAddedToWorkout` | В тренировку добавлено конкретное упражнение с параметрами (вес, повторения) |

### 1.2 Команды (Commands)
Команды — это намерения выполнить действие. Они инициируют события:

- `RegisterUserCommand` (вызывается через POST /v1/auth/register)
- `CreateWorkoutCommand` (вызывается через POST /v1/workouts)
- `AddExerciseCommand` (вызывается через POST /v1/workouts/{id}/exercises)

### 1.3 Сервисы и уведомления
- **Producer (Издатель):** Основной сервис Fitness API.
- **Consumer (Подписчик):** Сервис статистики (`statistics_consumer`). Он слушает события и обновляет аналитику (CQRS Read Model).

## 2. Проектирование Event-Driven архитектуры

### 2.1 Компоненты системы
Архитектура построена по паттерну **Publisher-Subscriber** через брокер сообщений.

1. **Event Producers:**
   - Класс `storage::Storage`: Инкапсулирует логику сохранения в MongoDB и отправки в Kafka.
   - Используется обертка `kafka::Producer`, настроенная на идемпотентность (`enable.idempotence=true`).

2. **Event Consumers:**
   - Отдельный процесс `statistics_consumer` (реализация на C++).
   - Подписывается на топики `user-events` и `workout-events`.
   - Обрабатывает сообщения асинхронно.

### 2.2 Типы событий и структура Payload
Все события передаются в формате **JSON**. Структура унифицирована:
```json
{
  "event_id": "unique_id",
  "event_type": "UserRegistered",
  "timestamp": "unix_time",
  "payload": { ...data... }
}
```

### 2.3 Поток событий
1. Клиент отправляет HTTP-запрос.
2. Handler валидирует запрос и вызывает `Storage`.
3. `Storage` выполняет запись в MongoDB (Write Model).
4. После успешной записи `Storage` публикует событие в Kafka.
5. HTTP-ответ возвращается клиенту (201 Created).
6. Consumer получает событие и обновляет Read Model (например, агрегирует статистику).

## 3. Проектирование взаимодействия через брокер сообщений

### 3.1 Выбор брокера
Используется **Apache Kafka**.
**Причина:** Высокая пропускная способность, поддержка replay events (повторной обработки), гарантии доставки и масштабирование через партиции.

### 3.2 Топики и Партицирование
- **user-events**: Партицирование по `user_id`. Гарантирует порядок событий для конкретного пользователя.
- **workout-events**: Партицирование по `workout_id` или `user_id`.

### 3.3 Гарантии доставки (Delivery Guarantees)
Реализована семантика **At-Least-Once** (минимум один раз):
- **Producer:** `acks=all` (лидер и реплики подтвердили запись), `retries=3`.
- **Consumer:** `enable.auto.commit=false`. Смещение (offset) коммитится вручную (`consumer.Commit()`) только после успешной обработки бизнес-логики.

## 4. Применение паттерна CQRS

### 4.1 Обоснование
В системе есть четкое разделение между операциями записи (создание тренировок, регистрация) и сложными операциями чтения (статистика, история активности).

### 4.2 Write Model (Команды)
- **Хранилище:** MongoDB (коллекции `users`, `workouts`).
- **Действия:** Вставка документов, добавление в массивы.
- **Триггер:** При изменении данных генерируется Event.

### 4.3 Read Model (Запросы)
- **Хранилище:** Отдельная коллекция в MongoDB (например, `user_statistics`), оптимизированная для чтения.
- **Синхронизация:**
  - Consumer слушает события `WorkoutCreated` и `ExerciseAdded`.
  - При получении события Consumer обновляет денормализованные данные в `user_statistics`.
  - Это позволяет делать выборку статистики за период за один запрос, без сложных агрегаций (aggregations) на лету.

## 5. Реализация простого Event-Driven сервиса

Реализация выполнена на C++ с использованием библиотеки `librdkafka`.

### 5.1 Producer
- Класс `kafka::Producer` использует Pimpl идиому для скрытия зависимостей.
- Настроен на асинхронную отправку сообщений.

### 5.2 Consumer
- Класс `kafka::Consumer` реализует цикл опроса (`Poll`) с таймаутом.
- Поддерживает ручное управление смещениями (Manual Commit).

### 5.3 Интеграция
Интеграция выполнена через компонент `storage::StorageComponent`, который внедряет зависимости (MongoDB Client + Kafka Producer) в слой бизнес-логики.
